# cppx 工业化建设路线

更新日期：2026-10-10。目标：可稳定集成到 Windows、Linux、macOS 产品中的通用 C++23 基础库。风险证据见 [项目评估](PROJECT_ASSESSMENT.md)。

构建、测试、安装与包分发统一使用 xmake/xrepo。优先验证现有命名模块链路，再根据具体工具链结果决定是否需要额外的接口兼容层。

## 验收原则

每个阶段交付可以构建、测试、评审的结果。修复以明确契约和回归用例为完成标准；平台支持以干净环境及仓库外消费者验证为完成标准。1.0 发布要以正确性、支持矩阵与真实使用反馈决定。

建议按一至两周的迭代节奏组织，一次迭代只承诺能独立验收的范围。下面是依赖顺序，不是工期承诺；工具链探针完成后再估计跨平台迁移工作量。

| 阶段 | 核心交付 | 进入条件 | 退出条件 |
|---|---|---|---|
| M0 可信验证基线 | 框架自检、修复 SECTION/失败报告、稳定 CI 配置、真实项目说明 | 当前代码 | Debug/Release 全量通过；新增自检证明修复前失败、修复后成功 |
| M1 跨平台最小闭环 | 工具链探针、接口/实现组织决策、Windows + Linux 首个消费者 | M0 | 两个平台干净构建及独立消费者运行；记录确切编译器和标准库版本 |
| M2 核心正确性 | JSON、error、时间、线程/队列、文件和日志的契约与修复 | M0；适配 M1 确定的实现组织 | 评估中的 P0 全关闭；关键故障路径有回归，已支持平台全通过 |
| M3 可交付的跨平台 Beta | 三平台矩阵、可选组件、安装导出、包管理和 API 文档 | M1、M2 | 三个平台消费者通过；源码包/安装包可从发布产物接入 |
| M4 长期可靠性与性能 | sanitizer、fuzz、压力运行、基准和资源预算 | M2、M3 | 稳定性、故障注入与代表性负载达标；报告可复现 |
| M5 1.0 发布 | 稳定 API、版本策略、迁移/支持文档和真实产品试点 | M4 | 无未解决 P0/P1；发布演练、回滚方案与至少一个真实产品集成验证 |

## M1：跨平台最小闭环

| 任务 | 工作内容 | 验收 |
|---|---|---|
| X01 | 添加工具链探针：普通 C++23 API、命名模块、import std 分开检测 | 明确编译器、标准库、构建工具组合及失败原因；不按编译器品牌推断支持 |
| X02 | 按 [ADR-0001](decisions/0001-cross-platform-baseline.md) 验证 error/string 的跨平台模块接入；受限组合再评估兼容接口 | 两个模块在 Windows 与 Linux 的 xmake 消费者中可用；公开类型和多翻译单元链接一致 |
| X03 | 提取控制台、时间转换、临时资源等平台差异 | 核心实现不泄漏 Windows 类型，系统链接按平台设置 |
| X04 | 创建独立 xmake 消费者，验证源码接入及原生模块包接入 | Windows/MSVC、Linux/Clang 构建并运行；包消费者只使用安装产物 |
| X05 | 加入第一个 Linux CI；macOS 与 GCC 建立探针任务 | Windows/Linux Debug/Release 必须通过；实验性组合明确标识，不算正式支持 |

当前新增 `xmake check-toolchain`，分别编译并运行 C++23 API、命名模块、import std 探针。新增 `xmake verify-consumer`，在独立目录验证源码接入与本地模块包接入；消费者导入全部 10 个模块，覆盖多翻译单元、公开宏头文件、宿主配置隔离和运行行为。

- [x] X01 探针工具：当前 MSVC 三项通过；缺失工具链返回非零并记录三项失败。
- [x] X04 Windows 独立消费者：Debug/Release 源码与本地包均通过；Debug 同时覆盖带空格的目录。
- [x] 源码嵌入时默认关闭 tests/examples，保留宿主项目名、版本和全局编译配置。
- [x] 原生模块包包含 `.cppm`、`.meta-info`、公开宏头文件、静态库及许可证。
- [x] CI 增加 Linux/Clang 18、Linux/GCC 14、macOS/Apple Clang 能力探针和报告归档配置。
- [x] 子项目配置隔离：探针与消费者执行前后根配置 SHA-256 一致；命名模块探针不构建标准库模块。
- [ ] Linux/macOS 远端探针实际运行；X02/X03 的平台适配与完整消费者验证。

M1 尚未完成：当前 Linux/macOS job 只要求常规 C++23 探针通过，模块能力分别记录；这不等于完整 cppx 平台支持。接口迁移必须由实际结果驱动，避免维护两套功能实现。

本次 M1 增量还通过 Windows Debug/Release 全量构建和各 11/11 测试程序、39 个 C++ 文件的 clang-format 18.1.8 检查及 `git diff --check`。具体工具版本、消费者结果和剩余验证范围见 [xmake 接入文档](XMAKE_INTEGRATION.md)。

## M2：关闭正确性风险

建议拆成以下独立变更，JSON 与生命周期缺陷优先。共享基础 error 的 API 决策先于其他模块大规模接口调整。

| 任务 | 对应风险 | 验收用例 |
|---|---|---|
| R01 错误模型 | E01 | T=E、move-only、会抛异常的移动、非默认构造 E、void 映射；优先评估 std::expected 作为内部存储，保留必要兼容门面 |
| R02 JSON 数据保真 | S01/S02 | 中文与 emoji 的 UTF-8/转义往返、代理对、int64/uint64 极值、2^53 附近、NaN/Inf/越界转换 |
| R03 JSON 严格解析 | S03 | 拒绝前导零/控制字符/残缺转义/尾部垃圾；限制输入大小、嵌套深度；提供带位置的错误 |
| R04 时间契约 | D01/D02 | UTC、正负时区偏移、毫秒、闰日、DST、非法日期和尾部垃圾；非 NUL 结尾 string_view |
| R05 定时器与线程 | C01/C02 | 可中断等待、幂等停止、一次性任务状态、回调异常、部分线程创建失败；明确回调内停止/析构约束 |
| R06 队列与线程池 | C02 | 关闭唤醒阻塞读写者、关闭后排空、提交拒绝、背压/容量、超时；避免线程池内部互等死锁 |
| R07 文件与临时资源 | F01/F02 | 排他创建、碰撞重试、并发唯一性、资源归属、移动后清理、短读/磁盘满/权限失败、原子替换 |
| R08 日志可靠性 | L01 | 并发切换级别、文件创建失败、轮转内容完整性、flush 失败；析构和错误上报策略明确 |
| R09 CLI/数学边界 | A01/M01 | 未知选项、长短选项一致、帮助返回宿主、-- 终止选项；整数极值/空输入/步进溢出 |

每项在修复前添加能揭示问题的用例；输入/编码语料尽量与成熟实现做差分校验。异步接口同时规定所有权、关闭状态、异常传播和最长阻塞行为。

## M3：可以交付与接入

- 三个平台建立固定的最低支持工具链和一个更新版本组合；macOS 优先 arm64，Linux 验证 Clang/libc++ 与 GCC/libstdc++ 的能力和支持范围。
- tests/examples 构建开关已提供；后续补齐 benchmarks 和可选组件，消费 cppx 不默认构建开发工具。
- 在已验证的 xmake 本地包基础上提供 xrepo 源码包配方、版本校验与私有仓库示例，再按发布流程接入 xmake-repo。
- 发布源码与必要头文件；模块 BMI/IFC 在消费者工具链上生成。静态库先形成可靠交付；共享库在符号导出、运行库和 ABI 策略明确后开放。
- 文档定义每个 API 的单位、编码、异常、错误类别、线程安全和生命周期。示例代码进入编译检查。
- 测试结果与日志保留为 CI 产物，建立机器可读报告；真实覆盖率工具可用后公布测量方式、排除项和关键路径覆盖。

## M4：稳定性与性能

- 在兼容组合上运行 ASan/UBSan，线程测试运行 TSan；先用最小探针核实工具对标准库/模块组合的支持，不把跳过检查描述为通过。
- JSON、字符串数值转换、时间与 CLI 引入固定语料和 fuzz；持久保存每个崩溃输入作为回归。每次变更短时运行，夜间扩大预算。
- 并发压力测试覆盖关闭竞态、取消、背压、线程异常；文件和日志引入权限、磁盘容量、失败注入。
- 为 JSON、线程池、channel 和日志建立代表性负载基准，记录吞吐、P50/P95/P99、峰值内存、分配次数及编译器选项。
- 先测量波动区间，再设回归阈值；正常 CI 的共享 runner 数据不能直接当作性能发布门槛。
- 在专用环境完成至少 24 小时运行，要求无崩溃、挂起、持续资源增长或未解释的数据丢失，并保存输入规模与资源曲线。

## M5：1.0 的完成标准

- [ ] 所有承诺平台上可以从发布产物构建独立消费者。
- [ ] P0/P1 缺陷关闭，关键路径故障与边界测试齐全。
- [ ] API、异常/错误、线程安全、Unicode 和资源生命周期契约明确。
- [ ] 静态/共享分发范围、编译器兼容性与 ABI 承诺明确。
- [ ] 建立语义版本、变更日志、弃用周期、迁移指南和缺陷响应流程。
- [ ] 至少一个真实下游产品完成集成、升级演练和稳定运行反馈。
- [ ] 性能/稳定性报告可复现，发布清单与回滚步骤完成演练。

## 下一次迭代的建议顺序

1. 运行已加入 CI 的 Linux/macOS 探针，按报告推进 X02 的 error/string 跨平台模块接入；Windows 源码/包消费者作为持续回归。
2. 用独立变更关闭 R01，再按 R02/R03、R04/R05、R07 的顺序修复高风险能力。
3. 将每个已修复模块迁移到 Windows/Linux 消费者中验证；达到 M2 后再扩大稳定 API 范围和发布 Beta。

每次结束更新任务状态、验证证据与剩余风险。阶段拆分允许实现工作分批进行，但不降低下一阶段的验收门槛。
