# ADR-0001：跨平台基础库与模块接口的边界

日期：2026-10-10。状态：xmake/xrepo 构建生态已确定；模块的跨平台适配细节待 M1 矩阵验证。

## 背景

产品目标已经明确为跨平台通用 C++ 基础库。现有项目采用 C++23、命名模块和 import std，只有 Windows/MSVC 的构建证据。三者不应绑定为一个不可拆分的产品门槛。

支持某种语法并不意味着标准库模块、依赖扫描、安装导出、sanitizer 和下游构建都可用。项目确定使用 xmake/xrepo 统一开发与分发，下游在自己的工具链下生成模块接口。

## 建议

保留 C++23 和现有命名模块接口，先分别探测 `std::expected`/`std::format` 等 API、命名模块以及 `import std`。使用 xmake 原生模块安装元数据和本地包完成消费者接入，后续提供 xrepo 源码包。

公共 API 保持 `cppx` 命名空间与显式模块职责。先用 error/string 验证 Linux 消费者及多翻译单元链接。若某个承诺工具链受标准库模块限制，再评估模块全局片段中的常规标准头文件，或共享实现的头文件兼容接口；兼容接口的类型身份、模板可见性和 ODR 必须单独验证。

当前与计划的物理分层：

```text
src/            命名模块、公开宏头文件；后续拆出私有平台适配
scripts/        xmake 验证与格式任务
tests/          单元、契约、并发、工具链探针、外部消费者
examples/       用户接入示例
benchmarks/     性能与资源基准（计划）
```

## 平台与交付策略

- Windows/MSVC、Linux/Clang 是第一条闭环；随后加入 Linux/GCC 和 macOS/Apple Clang。
- 常规 C++23、命名模块和 import std 分别记录能力；探针通过还需要完整库与消费者验证才能声明平台支持。
- 核心路径、编码、时间与并发逻辑尽量依赖标准库；Windows 控制台、排他文件创建等差异放入私有平台层。
- 首先交付源码与静态库集成；二进制明确编译器、架构、标准库和配置，不承诺跨编译器 ABI。
- BMI/IFC 按消费者工具链生成，不能作为通用预编译包。
- 构建、测试、安装和包分发使用 xmake/xrepo；最低 xmake 基线为 3.1.1，本地包受同一编译器/标准库/架构/模式约束。

## 代价与验证

坚持单一构建生态可以集中验证模块依赖扫描与分发。跨平台适配仍需维护编译器/标准库矩阵。库行为修复与接口组织调整应分别评审，保护现有 import 用户。

M1 必须包含源码模块消费者、安装包消费者、多翻译单元模板实例化、增量重编译。若引入兼容接口，还需增加混合消费者。无法支持的组合明确记录限制。

## 其他方向

常规头文件接口是工具链受限时可评估的兼容方式，当前先验证 xmake 的原生模块链路。降低语言标准或维护平行的功能实现都需要实际下游需求与维护成本证据。
